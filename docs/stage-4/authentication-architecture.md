# Stage 4 Authentication Architecture

Decision: [ADR-032](../adr/ADR-032-email-password-totp-authentication.md) (amends ADR-027). Code:
`internal/auth`, `internal/auth/passwords`, `internal/platform/crypto`. Sessions:
[session-management.md](session-management.md). MFA: [mfa.md](mfa.md). Authorisation: [rbac.md](rbac.md).

## 1. Factors

| Account | First factor | Second factor | Notes |
|---|---|---|---|
| USER | email + password | optional TOTP (+ 10 recovery codes) | unverified email may sign in; features that need it check `email_verified` (organisation creation, invitations) |
| STAFF | password (invitation-only account) | **mandatory** TOTP | DB CHECK: a STAFF session needs `mfa_verified_at` and a PASSWORD/WEBAUTHN first factor; staff step-up accepts TOTP only |

A verified phone number is **contact data only**: it is not a login factor and implies no identity or payout
verification (SIM-swap risk).

## 2. Passwords

- **Hashing:** Argon2id, PHC string (`$argon2id$v=19$m=65536,t=3,p=2$…`), parameters from config
  (`PASSWORD_HASH_*`; production refuses < 64 MiB). A semaphore bounds concurrent hashes
  (`PASSWORD_HASH_MAX_CONCURRENT`, default 4); when saturated the request gets `503` rather than queueing
  without limit. Hashes are upgraded on login when parameters change. A DB CHECK accepts only Argon2id PHC
  strings, so a plaintext or weak hash cannot be stored.
- **Measured cost** (this machine, Xeon 8160): ~141 ms per hash ([testing.md](testing.md) §4).
- **Normalisation:** NFKC; length counted in code points; control characters rejected.
- **Policy** (`passwords.Policy`): 12–256 characters by default (`PASSWORD_MIN_LENGTH`/`MAX`), not in the
  embedded list of the 10 000 most common passwords (SecLists, MIT licence), not containing the email, its
  local part or the display name, not a trivially repetitive string. Violations return
  `422 PASSWORD_POLICY_VIOLATION` with detail codes `TOO_SHORT`, `TOO_LONG`, `COMMONLY_USED`,
  `CONTAINS_PERSONAL_INFO`, `TOO_REPETITIVE`, `INVALID_CHARACTERS`. No composition rules (NIST SP 800-63B
  style). An online breached-password service (k-anonymity range queries) is **not** used — known issue KI-S4-04.
- **Timing:** unknown accounts verify against a dummy hash, so login time does not reveal whether an address is
  registered.

## 3. Flows

| Flow | Behaviour | Enumeration defence |
|---|---|---|
| Register | Creates USER + profile + unverified sign-in email in one transaction; emits `identity.email_verification_requested`. Concurrent registrations of one address collide on `uq_user_emails_login` (exactly one wins — tested with 10 in parallel) | Always `202 verification_sent`; an existing owner receives a "someone tried to register" email instead |
| Verify email | Consumes an `EMAIL_VERIFICATION` or `EMAIL_CHANGE` token atomically (`UPDATE … RETURNING`); single use | `400 TOKEN_INVALID` for every failure |
| Resend verification | New token invalidates the previous one (one live token per user+purpose, DB unique index) | Always `202` |
| Login | Throttle per IP and per normalised email (Valkey), verify password, refuse suspended (only after a correct password), then MFA challenge or session | `401 INVALID_CREDENTIALS` for unknown address and wrong password alike |
| Forgot / reset password | Token by email (TTL `PASSWORD_RESET_TTL`, 30 min default); reset replaces the password, verifies the email, revokes **all** sessions and pending MFA challenges, notifies the owner | Always `202` |
| Change password | Needs the current password; revokes other sessions; notifies | — |
| Change email | Needs the password; link to the new address; old address notified; the sign-in address changes only when the new one is confirmed, then all sessions are revoked | `202` even when the new address belongs to another account (nothing is sent) |
| Step-up | `POST /auth/step-up/verify` with password (users) or TOTP (users and staff); refreshes `sessions.step_up_at`; window `STEP_UP_MAX_AGE` | — |

## 4. Link tokens and codes

- Link tokens: 32 random bytes, base64url (43 chars). Generated by the **worker consumer at send time**, so the
  raw value exists only in the outgoing email; the database stores SHA-256. Outbox payloads carry IDs only.
  Links use `?token=` on `APP_PUBLIC_URL` pages; the web pages read and POST them, never log them.
- OTP (phone): 6 digits, HMAC-SHA-256 with the blind-index key over (challenge id, code); destination stored
  as an HMAC too; ≤ 5 minutes, ≤ 5 attempts (DB CHECKs), purpose-bound, a resend invalidates the previous code.
- Recovery codes: `xxxxx-xxxxx` (≈ 50 bits each), keyed hash per user, single use, regenerating supersedes the
  batch.
- MFA challenge: a random token in an HttpOnly, `SameSite=Strict` cookie (`fz_mfa`), stored hashed in
  `app.mfa_login_challenges` (`MFA_CHALLENGE_TTL`, 5 min default; DB cap 15 min; ≤ 5 attempts). No session exists until the second factor succeeds.

## 5. Throttling (distributed, `internal/platform/ratelimit`)

All limits are GCRA in Valkey with a protective local fallback (never fail open). Values are INTERNAL_RISK
starting points, not regulatory values.

| Policy | Key | Limit |
|---|---|---|
| `global.ip` | client IP (IPv6 /64) | `RATE_LIMIT_BURST` per `burst/RATE_LIMIT_RPS` |
| `auth.login.ip` / `auth.login.account` | IP / normalised email | 20 per 5 min / 5 per 15 min (every attempt counts) |
| `auth.register.ip` | IP | 5 per hour |
| `auth.password_reset.ip` / `.account` | IP / email | 5 / 3 per hour |
| `auth.verify_resend.ip` / `.account` | IP / email | 10 / 3 per hour |
| `auth.token.ip` | IP | 20 per 15 min (link-token submissions) |
| `auth.mfa.challenge` | challenge + user | 5 per 5 min |
| `auth.step_up` | user | 5 per 15 min |
| `auth.otp.send.user` / `.phone` / `auth.otp.verify` | user / E.164 / user | 5 / 3 per hour, 5 per 15 min |

There is no permanent lockout (an attacker cannot lock a victim out for longer than the window). The
per-account login limit is shared by every API replica (tested with two containers).

## 6. Keys

| Key | Use | Local | Production |
|---|---|---|---|
| `CSRF_SECRET` | HMAC for session-bound CSRF tokens | generated (≥ 32 chars) | secret manager (Stage 18) |
| `FIELD_ENCRYPTION_LOCAL_KEY` | AES-256-GCM for TOTP secrets (AAD = row id) | generated | **KMS — not implemented; production refuses to start** |
| `BLIND_INDEX_KEY` | HMAC for OTP codes/destinations, recovery codes | generated | KMS (Stage 18) |

Key IDs are stored next to ciphertext/hashes (`totp_secret_key_id`, `hmac_key_id`, `hash_key_id`) so rotation
can re-encrypt or re-hash lazily (rotation tooling is Stage 18).

## 7. What is deliberately not in Stage 4

OTP login, WebAuthn/passkeys, social login, device fingerprinting, risk-based authentication, real SMS
(Stage 15), KMS (Stage 18), CAPTCHA.
