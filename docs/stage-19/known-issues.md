# Stage 19 — Findings and known issues

Severity: CRITICAL / HIGH / MEDIUM / LOW. Category per brief §21-J. Every finding below was observed in this session.

## 1. Findings (defects found and fixed in Stage 19)

| ID | Severity | Category | Finding | Impact | Fix | Status |
|---|---|---|---|---|---|---|
| F-S19-01 | HIGH | implementation defect | Ledger lock-order inversion: `lockAndCheck` pre-locked only the balance rows a journal decreases; the entry triggers locked the others later. Journals moving funds between the same accounts in opposite directions (freeze/unfreeze, reserve/release, release/freeze on one campaign) deadlocked or hit the 3 s lock timeout | 200 concurrent opposite-direction postings: 86 posted, 5 deadlocks, 109 lock timeouts, 290 s. Refused postings were rolled back (no misstatement) but financial operations failed under realistic concurrency (e.g. a compliance freeze while a payout is released) | every SYNC row locked in ascending account id before entries (ADR-051 §3) | FIXED — 200/200, 0 deadlocks, 0 timeouts, 22.8 s |
| F-S19-02 | MEDIUM | implementation defect | Concurrent ledger synchronisations of one payout each wrote a RESERVATION_CONSUMED / LEDGER_POSTED event even when their link UPDATE matched no row | one consumption recorded **6 times** in the payout history (misleading evidence; reconciliation and staff views read it) | event only when the UPDATE linked the row | FIXED |
| F-S19-03 | MEDIUM | implementation defect | KI-S18-25: payout reconciliation judged payouts from the run's stale list and reported the legitimate completion → consumption window as a SEV1 RESERVATION_MISMATCH | false SEV1 exceptions; risk of alarm fatigue hiding real mismatches | re-read, settle the pending ledger sync through the Recover path, then evaluate; a failed recovery is reported with its refusal | FIXED |
| F-S19-04 | MEDIUM | implementation defect | KI-S18-22: payments in CREATED/PENDING/REQUIRES_ACTION/AUTHORISED were polled forever (every 10 min, no jitter) | unbounded provider traffic, attempts and audit growth per stalled payment; synchronized polling after outages | `PollHorizon`, `MaxStatusPolls`, jitter, POLL_BUDGET_EXHAUSTED reference | FIXED |
| F-S19-05 | LOW | implementation defect | Routine polls did not re-check under the row lock that the payment was still due: a sweeper that listed a payment could query it again just after another | duplicate status queries (read-only; no financial effect); budget accounting off | due re-check under `FOR UPDATE SKIP LOCKED` | FIXED (by construction; not reproduced before the fix in one round) |
| F-S19-06 | LOW | implementation defect | `Sweep` polled payments of every execution environment; a process without the adapter recorded "not sent" queries | a misrouted worker spends a payment's poll budget without asking the provider | sweep scoped to the process's environment | FIXED |
| F-S19-07 | LOW | implementation defect | `dispatch` classified the database's "no in-transit journal" refusal as DUPLICATE_SUBMISSION_ATTEMPT | misleading SEV2 exception next to the real LEDGER_POSTING_FAILED | not a duplicate: nothing is sent, the ledger failure is the record | FIXED |
| F-S19-08 | LOW | implementation defect | Concurrent payout reconciliation runs could both pass the "already under investigation" check and both record references for one payout (READ COMMITTED) | orphaned duplicate reference rows | payout row locked while recording | FIXED (by construction; not reproduced without it in 2 runs) |
| F-S19-09 | LOW | test/infrastructure limitation | KI-S18-24: `TestLedgerPeriodCloseMakerCheckerAndPriorPeriodPostings` drew a random 1900–1999 month; on the persistent development database 19 of 1 200 were already closed by earlier runs, so a repeat draw failed with LEDGER_PERIOD_STATE | intermittent local failure (~1.6 % per run and rising) | the test draws a month no earlier run used | FIXED (root cause by analysis; deterministic reproduction not run) |

| F-S19-10 | MEDIUM | implementation defect (performance) | Provider health derivation (`psp.ProviderHealth`), run by every payout eligibility check at request and before submission, scanned the provider's whole append-only call history (window query 93 ms, circuit lookups 79 ms each, distinct-currency enumeration 200 ms per operation on 1.26 M development rows) | ~0.6 s per derivation, growing linearly with every provider call ever made; payout requests and submissions slow down over time | three indexes (migration `20261024090100`) and circuit currencies enumerated from circuit events only (same result) | FIXED (benchmark-results.md §3) |
| F-S19-11 | LOW | implementation defect (API contract) | The OpenAPI `PaymentReconciliationReferenceS8.reason` enum lacked CONTRADICTORY_EVIDENCE (allowed by the database since Stage 9) | clients generated from the contract could reject a real response value | enum completed (and POLL_BUDGET_EXHAUSTED added) | FIXED |
| F-S19-12 | HIGH | implementation defect | Payout attempts: `startAttempt` numbered an attempt (`max + 1`) before any lock, and `recordObservation` locked its attempt row before the payout row — the reverse of the attempts guard trigger (payout row first). Concurrent status queries of one payout (several workers' poll jobs, a staff status check) collided on `uq_payout_attempts_no`, deadlocked, timed out, and could strand an IN_FLIGHT status attempt (which Recover later turns into a false UNKNOWN) | 64 concurrent status queries of one payout: 21 ok, 43 failed (39 duplicate numbers, 2 deadlocks, 2 lock timeouts), 68 database deadlocks, 1 stranded IN_FLIGHT attempt; the endurance run logged 98 deadlocks, all in this pair. No duplicate provider instruction (CREATE_PAYOUT stays guarded) and no money effect | payout row locked first in both paths; a status query is skipped while another of the same payout is in flight | FIXED — 64/64 ok, 0 failed, 0 deadlocks, no duplicate numbers (`TestFinancialPayoutConcurrentStatusQueries`) |
| F-S19-13 | MEDIUM | implementation defect (detection gap) | Ledger reconciliation (Stage 10, journals vs payment facts) scanned the **oldest** 10 000 payment-sourced journals (`ORDER BY posted_at LIMIT 10000`); once the ledger held more, every new journal was outside the window and never compared with its payment. Found because the load runs pushed the development ledger past 10 000 synthetic captures (16 562) and `TestLedgerReconciliationFindsExceptionsAndWorkflow` stopped finding its own planted AMOUNT_MISMATCH | silent loss of mismatch detection at volume (inactive today: no production postings exist) | newest 10 000 first, like the payout and fee reconciliations (journals are immutable; older ones were checked by earlier runs) | FIXED; full-history incremental reconciliation is KI-S19-09 |
| F-S19-14 | LOW | implementation defect | A Stage 17 reconciliation run whose execution context ended (deadline, shutdown) was left RUNNING: `ExecuteRun` wrote FAILED with the same, already-cancelled context, so the update failed too. The scope stayed blocked until `ReapStaleRuns` (10 min of stale heartbeat); a run executed with a future test clock had a future heartbeat and blocked its source indefinitely on the development database (3 Stage 17 tests then timed out waiting for a run slot) | blocked reconciliation scope for 10 min (or longer with a skewed clock) | FAILED is written with a non-cancelled, bounded context; the stuck development run was released through `ReapStaleRuns` itself (WORKER_LOST) | FIXED — a timed-out run is now FAILED / RUN_ERROR immediately (observed) |

No CRITICAL finding. No financial invariant failure (imbalanced journal, negative balance, duplicate posting, duplicate
provider instruction) was observed in any Stage 19 run.

## 2. Known issues (open)

| ID | Severity | Category | Issue | Impact | Next step |
|---|---|---|---|---|---|
| KI-S19-01 | MEDIUM | operational readiness | Ledger posting throughput is bounded by the global audit chain lock (each posting writes an audit event; writers serialise): ~155–180 journals/s at 8–16 writers on this host. A posting holds its balance rows while it waits for that lock, so hot accounts convoy | capacity ceiling of the single-node design; hot campaigns queue | capacity target and design decision (e.g. per-chain partitioning) — needs an approved target first; audit integrity is not weakened (ADR-050) |
| KI-S19-02 | LOW | implementation | The F-S19-01 fix costs ~3–9 % posting throughput and 1–5 ms p50 at 8–16 writers in one before/after run each | small; within the measured noise not yet established | repeat the comparison on production-like hardware |
| KI-S19-03 | LOW | implementation | The completion → consumption window (KI-S18-25) still exists for milliseconds, or until Recover after a crash; it is named and settled, not removed | none for reconciliation; staff views can show COMPLETED with an ACTIVE reservation for that moment | accepted design (cross-pool transaction unavailable, ADR-042) |
| KI-S19-04 | MEDIUM | provider-selection dependency | `PollHorizon` 72 h and `MaxStatusPolls` 500 are internal safety defaults, not provider-documented values | a real provider may need other bounds | PCR-010 at provider selection; owner approval of the values |
| KI-S19-05 | LOW | test limitation | The cancel-vs-submit race resolved to "cancel wins" in all 3 rounds; the "submission wins" branch is asserted but was not exercised | branch coverage | force it with a barrier on the eligibility gather in Stage 20 |
| KI-S19-06 | LOW | test limitation | F-S19-05 and F-S19-08 were not reproduced before their fixes (narrow windows) | fixes argued by construction | barrier-based reproduction if a hook point is added |
| KI-S19-07 | LOW | test limitation | The worker kill (F-06) landed between provider calls; the crash *during* a provider call is covered by the Stage 11 WORKER_RESTART case, not by a process kill | — | — |
| KI-S19-08 | LOW | test limitation | A stale worker finishing after River lease expiry was not separately forced (no injection point in River) | covered by idempotency tests | — |
| KI-S19-09 | MEDIUM | operational readiness | All three internal reconciliations are windowed full scans, not incremental: payouts the newest 5 000 (with a provider status query per submitted payout: ~38 s for one complete run over ~2 850 development payouts, `TestFinancialPayoutReconciliationInterrupted`; 17–19 s maxima under load), fees the newest 5 000 assessments, ledger the newest 10 000 payment journals (F-S19-13). Older records are not re-checked by later runs | run time grows with volume; a record that becomes inconsistent after leaving its window is not re-detected (Stage 17 statement reconciliation remains the settlement control) | incremental reconciliation with a changed-since watermark before production volumes |
| KI-S19-10 | LOW | test limitation | Volume tiers: ledger to 10⁵ journals in this stage (10⁶ in Stage 10); payments and payouts only to the thousands created through the real domain model | no 10⁵–10⁶ payment/payout table measurements | build a domain-faithful bulk generator |
| KI-S19-11 | INFO | governance | All load numbers come from one development host with simulators; no SLO, RPO/RTO or capacity target is approved | numbers are baselines, not capacity | owner-approved targets |
| KI-S19-12 | LOW | implementation | Lock timeouts (55P03) are not retried inside `PostOnce` (callers retry on their next run) | an isolated timeout fails one attempt | revisit with production lock metrics |
| KI-S19-13 | MEDIUM | operational readiness | The single worker (`WORKER_CONCURRENCY` 4) is the throughput bottleneck at 16 sustained load workers: in the post-fix 30-minute endurance run the notifications queue backlog grew to ~15 000 ready jobs (`outbox.deliver` avg 263 s, max 546 s from creation to completion; 13 561 still waiting at the end) and the financial default queue's average latency rose to 8.5 s (max 19.1 s). The Stage 15 queue separation kept financial work flowing; nothing failed or duplicated | notices minutes late; financial jobs seconds late at that load | size worker concurrency / worker processes against an approved target (Stage 20) |
| KI-S19-14 | LOW | implementation | An indeterminate answer to a payout *status query* (timeout, 5xx, a crashed status attempt) moves a SUBMITTED/PROCESSING payout to UNKNOWN (Stage 11 design: conservative; UNKNOWN is polled and never resubmitted) | false UNKNOWNs after status-query failures; reconciliation after the horizon | revisit with the provider's status semantics (PCR-010) |
